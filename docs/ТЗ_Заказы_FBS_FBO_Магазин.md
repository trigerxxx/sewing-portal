# Заказы и поставки: FBS, FBO, магазин

Анализ существующей архитектуры и проект реализации · 04.11.2026

## 1. Что уже есть

| Направление | Сейчас | Чего нет |
|---|---|---|
| **FBS (Wildberries)** | только Excel-выгрузки: «жск перевод» (210 строк), «ККМ перевод» (172) — это отчёты WB, а не живые заказы | API, кабинеты, токены, автообновление |
| **FBO** | нет вообще; «паставка Алтын» — складская отгрузка, а не заявка клиента | заявки, статусы поставок |
| **Магазин** | работает: корзина → заказ; клиент авторизован | единый список, история статусов |
| **Единый раздел** | нет; складские «Поставка» и клиентские «Мои заказы» раздельно | фильтры, история |

Хранилище сейчас двойное: реестр `data/склад_реестр.json` (заказы магазина) и SQLite `orders`
(0 строк, схема минимальная). Складские отгрузки — Excel `паставка *`.

Вывод: **ни FBS-интеграции, ни кабинетов, ни истории статусов в проекте нет** — это новая часть.

## 2. Принципы (чтобы не плодить дубли)

1. Одна таблица заказов на все три направления — `orders` с полем `type`.
2. Одна таблица позиций — `order_items`.
3. Статусы единые (7 штук), различается только набор допустимых переходов.
4. Новые таблицы только те, которых физически нет: `wb_cabinets`, `order_status_history`.
5. Складские движения остаются в `shipments`; заказ ссылается на отгрузку, а не дублирует её.
6. Excel-листы остаются отчётами/историей, а не источником истины для FBS.

  WHERE external_id IS NOT NULL;

### 3.2 Новые таблицы

```sql
CREATE TABLE wb_cabinets (
    id           TEXT PRIMARY KEY,        -- короткий код: 'zhsk', 'kkm', 'aat'
    name         TEXT NOT NULL,           -- «ЖСК», «ККМ», «Алтын»
    wb_name      TEXT,                    -- название в кабинете WB
    token_ref    TEXT,                    -- ключ в secrets/wb_tokens.json (не сам токен!)
    active       INTEGER DEFAULT 1,
    last_sync_at TEXT,
    last_error   TEXT
);

CREATE TABLE order_status_history (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    order_id   TEXT NOT NULL REFERENCES orders(id) ON DELETE CASCADE,
    from_status TEXT,
    to_status   TEXT NOT NULL,
    actor       TEXT,                     -- логин или 'wb-api'
    at          TEXT NOT NULL,
    comment     TEXT
);
CREATE INDEX ix_history_order ON order_status_history(order_id, at);
```

## 4. Статусы

| Код | Название | Кто ставит |
|---|---|---|
| `new` | Новый | система (API/клиент) |
| `processing` | В обработке | склад/менеджер |
| `picking` | Собирается | склад |
| `picked` | Собран | склад |
| `shipped` | Отправлен | склад |
| `done` | Завершён | система/менеджер |
| `cancelled` | Отменён | клиент/склад/менеджер |

Допустимые переходы:

| Тип | Цепочка |
|---|---|
| FBS | new → processing → picking → picked → shipped → done |
| FBO | new → processing → picking → picked → shipped → done |
| SHOP | new → picking → picked → shipped → done |

Отмена разрешена из любого статуса, кроме `done`. Каждый переход пишет строку в `order_status_history`.

## 5. FBS через API Wildberries

### 5.1 Схема работы

1. Токен кабинета хранится **вне кода**: `secrets/wb_tokens.json`, права 600, в таблице — только `token_ref`.
2. Фоновый поток раз в N минут (по умолчанию 5) и кнопка «Обновить сейчас».
3. Для каждого активного кабинета:
   - получить новые сборочные задания;
   - получить текущие статусы по уже известным;
   - обновить/создать заказы, записать историю;
   - сохранить `last_sync_at`, при ошибке — `last_error`.
4. Идемпотентность: уникальный индекс `(type, cabinet_id, external_id)` — повторный импорт не создаёт дубль.
5. Заказы разных кабинетов не смешиваются: кабинет — обязательное поле для FBS.

### 5.2 Сопоставление товаров

WB отдаёт `nmId`, `barcode`, `article`, `skus`. Наши товары имеют полное имя
`Категория/модель/цвет/размер`. Способы:

1. по баркоду (лист «лист для штрих кодов») — точное совпадение;
2. по артикулу WB (столбец «Артикул Wildberries»), если заполнен;
3. вручную: таблица соответствий `wb_sku_map(cabinet_id, external_sku, product_id)`.

Если не нашлось — заказ создаётся, позиция помечается `product_id = NULL`,
на экране — «требует сопоставления». Это лучше, чем терять заказ.

### 5.3 Токены

Хранить в файле с правами 600 вне папки проекта не обязательно, но обязательно:
- не писать в логи;
- не показывать в интерфейсе (только «токен задан/нет»);
- уметь менять без перезапуска.

## 6. FBO — заявки клиентов

1. Клиент в кабинете создаёт заявку: кабинет WB, товары, количество.
2. Имя и ID берутся из профиля — повторно не спрашиваем.
3. Заявка = `orders(type='fbo')` + `order_items`.
4. Дальше обычная цепочка статусов; после `picked` склад оформляет фактическую отгрузку
   (`shipments`), после `shipped` — передача в кабинет.
5. История статусов обязательна, отмена — только до `shipped`.

## 7. Магазин

Используем существующую корзину. Меняем только точку сохранения:
сейчас заказ уходит в реестр JSON и частично в SQLite — оставляем **одну** таблицу `orders(type='shop')`,
клиент и дата подставляются автоматически из сессии.

## 8. API

| Метод | Назначение |
|---|---|
| `GET /api/orders?type=&cabinet=&status=&from=&to=&q=` | единый список с фильтрами |
| `GET /api/orders/{id}` | карточка + история |
| `POST /api/orders/{id}/status` | смена статуса с проверкой перехода |
| `POST /api/orders/shop` | оформление из корзины (замена текущего) |
| `POST /api/orders/fbo` | заявка клиента |
| `GET/POST /api/cabinets` | кабинеты (admin) |
| `POST /api/wb/sync` | ручная синхронизация |
| `GET /api/wb/status` | статус синхронизации и ошибки |

## 9. Интерфейс

Один раздел «Заказы»:

- вкладки: **Все · FBS · FBO · Магазин**;
- фильтры: тип, кабинет, статус, период, поиск по номеру/товару;
- таблица: номер, тип, кабинет, клиент, дата, позиции, сумма, статус;
- карточка: позиции + история статусов + кнопки перехода;
- на телефоне — карточками, кнопки статусов крупные.

Раздел включим через `config.json → visible`, когда будет готов.

## 10. Миграция

1. Существующие заказы магазина из реестра → `orders(type='shop')`.
2. «жск перевод»/«ККМ перевод» — историческая выгрузка: импорт со `source='excel'`,
   без статусов (или всем `done`), чтобы была история.
3. Склад не трогаем: `shipments` продолжают жить как раньше.
